# Evidence Gate（证据先行门控）

## 核心铁律

**没有新鲜的验证证据，就不能声称完成。** 任何"已完成/成功/已修复/达标"的声明，必须附带可复核的证据链。

## 触发条件

- 声称任务完成或阶段完成时
- 说"修好了""写完了""通过了"之前
- 交付物交接前

## 流程（四步）

1. **验证动作**：运行验证命令/测试/检查（测试输出、编译结果、数据校验、引用核对）
2. **证据引用**：引用具体输出（文件:行号、命令输出、测试统计），不引用"应该没问题"
3. **门控判定**：证据通过 → 才可声明；证据失败或缺失 → 修复后重新验证，禁止绕过
4. **记录**：验证命令与结果写入交付记录

## 反模式（禁止）

- ❌ "代码应该能跑" → ✅ "pytest 23 passed, 0 failed（输出见 ci.log:12）"
- ❌ "文献应该真实" → ✅ "Crossref API 返回 200，DOI 10.1007/4-431-26925-8_7 匹配"
- ❌ "字数应该达标" → ✅ "正文 3996 词（脚本统计，见 report.md:3）"

## 与 HARD-GATE 的配合

- **HARD-GATE（设计门）**：未经用户批准设计前，禁止写代码/实施动作——适用于每个项目，无论多简单。简单项目恰恰是未检查假设浪费最多工作的地方。
- 流程：探索上下文 → 逐个澄清问题 → 提出 2-3 方案带权衡 → 分段展示设计逐个获批 → 写设计文档 → 规格自审
- 本项目实战案例：通用数据校验（某指标实测值复核后写入正文，而非凭记忆写估算值——证据门控直接拦截了一处数据不实）
