# Cross-Model Quality Audit

## When to Use

When **existing work was done by model A (weaker/cheaper) and needs to be reviewed by model B (stronger)**. Typical triggers:

- User says "model X did this work, check its quality" 
- Model A ran during a quota-limited period (e.g. deepseek-v4-flash after glm-5.2 hit 429)
- Work was done by a subagent (delegate_task) with a different model
- You inherited code/docs generated by another model and need to QA it

## Distinction from Standard Verification

| | Standard Phase-4 Verification | Cross-Model Quality Audit |
|---|---|---|
| **When** | After YOU just created the deliverable | After SOMEONE ELSE (or different model) created it |
| **Assumption** | The work is probably correct | The work may have systemic quality issues |
| **Approach** | Check against spec | **Proactively hunt for defects** — imagine you're finding problems |
| **Mindset** | "Does this meet requirements?" | "What did the other model get wrong?" |

## Workflow

```
Layer 1: Model B (stronger) — thorough audit
  → Read ALL files in the skill/deliverable
  → Check: API format correctness, data consistency (e.g. chroma_key format),
           rule compliance (e.g. animation prompt constraints), documentation
           completeness, code clarity
  → Create issue list (with severity: 🔴 severe / 🟡 medium / 🟢 light)
  → Fix all issues immediately

Layer 2: Model C (different family) — cross-check
  → Use a model from a DIFFERENT API provider than B
  → Provide the same file set + the list of already-fixed issues
  → Ask: "what did Model B miss?"
  → Evaluate each new finding — some may be false positives from context truncation
  → Fix legitimate new issues

Layer 3: Model B — final verification
  → Verify all scripts parse correctly (syntax check)
  → Verify cross-file data consistency (e.g. write format == read format)
  → Verify rules not violated (e.g. no forbidden props in prompts)
  → Verify test artifacts exist (if applicable)
  → Report pass/fail per check
```

## Common Defect Patterns from Weaker Models

**Data format inconsistencies** — one file writes `chroma_key` as a string `"#FF00FF"`, another reads it as a dict `{"hex":...}`. Always verify write-vs-read format across all files in the data pipeline.

**Rule/text constraints not embedded in code** — a prompt generation script writes "holding a magnifying glass" even though the animation spec forbids new props. The weaker model writes what it "thinks makes sense" rather than checking the spec.

**Missing defensive code** — no fallback paths (e.g. rembg→chroma-key), no retry logic, no file-exists checks. The weaker model writes the happy path only.

**Incomplete documentation** — missing dependency lists, environment variable tables, setup steps, troubleshooting guides. The weaker model assumes "the user will figure it out."

## Verification Checklist for Code Audits

```
□ All scripts pass Python syntax check (ast.parse)
□ Cross-file data format consistency (write format == read format)
□ No rule/constraint violations in text content (prompts, descriptions)
□ Defensive code present (fallbacks, retries, existence checks)
□ Documentation covers: dependencies, env vars, setup, troubleshooting
□ Test artifacts exist (if test run was done previously)
□ Function-level docstrings present on all public functions
□ No unused imports or dead code
```
